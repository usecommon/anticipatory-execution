# Research safeguards and numerical-impact policy — v0.5

## Frozen thesis and scientific target

**Do not predict what the user will type next. Predict what work will not need to be undone.**

The question remains whether temporal/cross-layer dynamics of a frozen autoregressive foundation model predict future action non-revision beyond the observed prefix, observable outputs (B1), and a single hidden-state representation (B2). H2 remains the primary novelty-critical comparison; H3 tests trajectories beyond a snapshot. Product viability and internal-state scientific value remain distinct outcomes. No novelty claim is broadened to early intent prediction, early tools, or speculative execution itself.

This is an instrumentation correction, not a favorable-result optimization. No hypothesis, endpoint, action label, split, bootstrap rule, minimum practical effect or numerical tolerance changes. The supplied protocol is preserved; this versioned addendum records the corrected measurement implementation.

## Results may not be numerically neutral

FP32, attention implementation, padding policy, batch shape and cache policy can change hidden states, logits and derived features. Removing shape artifacts may reduce, eliminate or reverse an apparent internal-state advantage. A G0 pass establishes measurement validity only within its declared execution scope; it is not evidence for H1–H4 or S1.

The v0.5-to-v0.3 bridge compares the hardened implementation to the prior canonical FP32 path on the same eight fixtures. Passing it establishes local regression continuity only. It does not establish equivalence to historical BF16 runs, arbitrary prompts, alternative devices or the missing historical 24/80 experiment. Numerical-impact claims must state their comparison scope.

## Version separation and downstream reanalysis

Every extraction artifact carries a contract ID tied to code, model/tokenizer files, framework, precision, attention, width, hardware and cache policy. Keep historical BF16, v0.1/v0.2 diagnostics, v0.3 canonical states and v0.5 states as separate versions. Never concatenate incompatible features or reuse old fitted probes/calibration as though the correction were neutral.

Once G0 and G1 permit development work, regenerate affected B1/B2/M features from the same pinned forward configuration, refit affected development-only transforms/probes/calibrators and report both favorable and unfavorable changes. Do not compare BF16/cached B1 outputs with FP32/canonical M states as a test of incremental internal information. Never use confirmatory labels, performance, layer selection or effect direction to choose the numerical configuration, cases or tolerance.

Do not tune the pipeline to recover old layer accuracies or the historical failure count. A disappearing scientific advantage after correction is a valid negative finding. Keep product and scientific conclusions separate.

## Coverage, future-information boundaries and failures

The 128-token width is an advance implementation constant independent of unseen suffixes. Each observed text prefix is sliced without whitespace normalization and tokenized independently. Future text is used only for causal-invariance QA fixtures, never as an extraction-entrypoint input field.

A whole job must pass preflight before any forward. An overlength or malformed item blocks the job visibly; no truncation, silent skipping, adaptive width, bucket changes, cache or native-batch fallback. Do not selectively remove long or late-revising examples. The eventual development benchmark's length distribution is not established by this QA set. Before any development extraction, check its coverage; if 128 is insufficient, select a larger global width without consulting outcomes and rerun G0. Confirmatory data remain untouched.

The original native-mode failures keep their original FAIL status. A supported canonical contract may pass while excluded modes remain failed, provided the code enforces their exclusion and the gate explicitly states the scope. This is not a tolerance waiver or a claim that the underlying kernels have been repaired.

## Cost and product implications

Fixed-width FP32, serialized batching and no KV reuse can increase latency, memory and compute. Record those costs, including rejected jobs and wasted work. A valid measurement pipeline can still fail the matched-compute latency hypothesis. Do not present instrumentation runtime as an achieved product latency advantage or omit extraction overhead from future S1 comparisons.

Faster execution, a different width, batching, cache reuse, dtype or hardware requires separate instrumentation validation and explicit configuration provenance. Attention/KV features remain exploratory and unvalidated where they require excluded modes.

## Gate progression

The current executable entrypoint permits only `partition='qa'`; development and confirmatory requests are rejected before model inference. A scoped G0 PASS does not automatically enable those partitions. G1 still requires two independent annotators, Cohen's kappa >=0.70 and the prescribed adjudication process. The owner key is not independent annotation.

No confirmatory extraction is authorized in this task. No training or scientific efficacy evaluation occurs in the closure runs. Model parameter values are never updated; rejection tests may temporarily toggle training/gradient flags but must reject inference before restoring them.
