# Prefix-only early directory work — v0.1

**Eight early listings were reused in correct final-task completions without a second listing.** These are execution witnesses from an authored deterministic rule on four exposed source records (three instruction groups), not model predictions, usefulness labels or thesis evidence.

## Frozen boundary and policy

All nine fixed selected records were retained at 6/12/18 literal-word checkpoints: 27 scheduled and eligible opportunities. Candidate dispatch did not depend on whether the completed task had a supported checker. A separate audited worker received only exact prefix, initial cwd and one constant read-only ls schema. No final instruction, directory contents, task/source IDs, expected outputs or receipts entered that worker. This is separate-process code isolation with inspected fixed source, not an OS sandbox or independent model-based generation.

The rule proposes current-directory enumeration after a listing/file-directory trigger, includes hidden entries by default, respects the literal observed exclusion phrase and abstains for recognized target mismatches requiring navigation. It is a simple engineering policy designed after exposure to these tasks. It is neither calibrated nor a test of internal states. See the frozen [plan](PLAN.md), [policy](policy.py), [payloads](preparation_02/PAYLOADS.jsonl) and [opportunity denominator](preparation_02/OPPORTUNITIES.jsonl).

Initial cwd is declared observable setup metadata. Raw original state remains tool-private/evaluator-only. This context differs from the earlier plain-prefix model extraction; old states are not reused as a comparison against new contextual observables.

The listings were correct against independently specified final requirements and linked to the early receipts; static environment snapshots matched. Both identical-instruction records remain linked as one instruction group while keeping their different source environments.

A positive witness supports the possibility of reuse under this executor/environment. It does not assign binary usefulness or fractional utility, estimate a natural success rate, establish calibrated risk, validate human G1, or support H2/H3. Unsupported outcomes remain unresolved rather than negative. New candidate artifacts differ from earlier AI-rated preparations; their old labels were not transferred or overwritten.

**Freshness is privileged here:** the offline evaluator verifies the complete static environment and final requirements. This is an oracle-assisted reuse witness, not a deployable reuse policy. Real validation costs and observable freshness evidence remain open. All supported original targets lack hidden entries, so this sample still cannot test hidden-constraint invalidation.

## Operations, dependencies and failures

Recorded counts: 12 early ls calls, four fresh final ls calls, 12 evaluator reference ls calls, 27 per-episode setup pwd calls and nine metadata setup pwd calls. Each checkpoint is a fresh episode; counts do not represent a cumulative streaming policy. On supported tasks, eight early plus four final listings replace 12 final-only listings: work shifts earlier, total listing work does not decrease. The four other early listings have unresolved utility because their final checker is unsupported. Reference checks and simulator/checker overhead are separate. No measured latency/compute benefit is claimed.
